# ADR-007 渠道接入：统一业务接口与渠道适配边界

- 状态：Accepted（已接受）
- 日期：2026-11-25
- 阶段：P0 / ST-0.5（决策固化）
- 业务实现阶段：P14
- 关联约束：`specs/ST-0.5.md` R4、`docs/spec/AI电商-Spec文档包-v2/03-API契约与错误码.md` §3.5/§3.6

## 背景

系统需要同时支持 Web、H5、小程序、App（Tauri）和开放平台。各渠道在登录、支付、分享、推送、扫码和归因上使用不同协议与能力；如果这些差异进入订单、支付、身份或营销等业务模块，就会形成按渠道复制的流程和条件分支，使契约、测试与后续渠道扩展难以维护。

开放平台还面临第三方应用身份授权、请求防伪与防重放、调用审计、配额治理以及 Webhook 可靠投递问题。同时，渠道接口演进不能以牺牲既有调用方为代价，破坏性变更必须可评审、可迁移并保留兼容窗口。

ST-0.5 只固化上述决策和验收边界，不交付渠道功能。统一接口、适配器、回调、OAuth2、签名、Webhook 及相关业务能力的实现均归 P14；本 ADR 的存在不代表任何渠道适配器已经实现或联调通过。

## 决策

### 1. 统一上下文与业务接口

所有渠道请求经适配后，业务层只接收统一上下文：

```text
ChannelContext{channel, device_id, open_id?, scene?}
```

字段语义如下：

| 字段 | 是否必需 | 统一语义 |
|---|---|---|
| `channel` | 是 | 请求来源渠道的稳定标识，用于上下文记录、审计和观测，不作为业务流程分支条件 |
| `device_id` | 是 | 渠道侧设备或安装实例标识；由适配层按统一口径提取或生成，不承载渠道 SDK 的原始会话对象 |
| `open_id?` | 否 | 渠道身份体系下已解析的外部用户标识；缺失表示该渠道或当前流程没有此身份，不直接等同于内部用户 ID |
| `scene?` | 否 | 小程序 `scene`、深链或落地页等入口归因信息；由适配层转换为统一归因语义 |

采用“一套业务接口，多渠道壳”的结构：业务用例只依赖统一请求、统一上下文、统一结果和统一错误语义；多渠道壳只允许在**协议与能力**上分叉。不得把第三方 SDK 类型、原始回调报文、渠道专有错误码或渠道页面参数泄漏到业务接口。

能力不支持是适配层返回的明确结果，例如 H5 无推送能力；业务层不得通过识别渠道名称规避或模拟该能力。新增渠道只能实现同一适配契约，不得要求业务用例增加渠道专属流程。

### 2. 渠道差异的唯一归属

所有渠道差异只能在 `channel` crate 内实现，包括协议编解码、渠道鉴权、SDK 交互、参数转换、能力探测、签名验签、渠道错误映射和渠道应答格式。

业务代码禁止出现 `if channel == "miniapp"`、`match channel` 后执行渠道专属逻辑，或功能等价的字符串判断、配置开关和隐式分支。审计、日志和指标可以使用 `channel` 作为分类标签，但不得借此改变业务规则。

适配器只负责外部协议与统一模型之间的转换；订单、支付入账、身份绑定、通知业务规则和归因计算等业务决策仍由对应业务模块拥有。禁止为绕过此边界而把业务规则下沉到某个渠道适配器。

### 3. 六类能力的适配边界

| 能力 | 渠道侧职责（仅 `channel` crate） | 统一业务侧职责 |
|---|---|---|
| 登录 | Web 密码/微信扫码、H5 微信授权、小程序微信静默登录与手机号授权、App 密码/微信/Apple、开放平台 OAuth2 的协议交互及凭据校验 | 基于统一身份结果执行内部账号查找、绑定、会话与权限流程，不读取渠道授权码或 SDK 会话细节 |
| 支付 | 支付宝、微信 H5、小程序支付、App 原生 SDK、服务商模式的下单参数转换；回调验签、报文解析和渠道格式应答 | 查单并校验支付单和金额，按统一支付结果幂等入账、更新订单并发送领域事件；不解析渠道原始回调 |
| 分享 | 链接卡片、链接/海报、小程序转发卡片、系统分享等能力的构造和调用 | 提供统一分享内容、目标对象与归因信息，接收统一能力结果，不选择渠道专属卡片或 SDK |
| 推送 | Web Push、小程序订阅消息、APNs/FCM、开放平台 Webhook 的凭据、协议和投递结果转换；H5 明确返回不支持 | 表达统一通知意图、接收统一投递状态，不感知设备令牌格式或渠道报文 |
| 扫码 | Web/H5 相机、小程序扫码 API、App 原生扫码的权限、协议与结果规范化 | 只处理统一扫码结果及其业务语义，不处理相机或原生扫码 API |
| 归因 | URL 参数、URL + 落地页、小程序 `scene`、App 深链、开放平台应用标识的提取与标准化 | 基于 `ChannelContext` 和统一归因输入执行归因规则，不判断入口来自何种渠道 |

支付适配层返回的渠道应答必须遵循渠道要求，不能用统一业务 JSON 替代；但应答格式差异不得反向影响业务入账结果。扫码、分享等前端交互由对应渠道壳通过 `channel` crate 暴露的统一能力接口触发，渠道特有调用与转换规则仍只能位于该 crate。

### 4. 开放平台安全与治理

开放平台接入同时满足以下要求，OAuth2 授权不能替代请求签名：

- **OAuth2**：应用授权、令牌换取、刷新、撤销和 scope 校验均在开放平台适配边界完成；业务层只接收已授权的应用或用户主体及统一上下文，不接触客户端密钥和令牌端点细节。
- **请求签名**：开放接口使用应用级密钥进行 HMAC-SHA256 签名，覆盖约定的规范化请求内容和防重放参数；验签失败不得进入业务用例。
- **5 分钟时间窗**：请求时间戳与服务端时间相差不得超过 5 分钟，超窗请求直接拒绝，不能仅记录告警后放行。
- **nonce 去重**：按应用维度对 nonce 去重，至少覆盖签名时间窗；重复请求直接拒绝。去重键必须包含应用标识，避免不同应用互相影响。
- **调用日志**：记录应用标识、接口、时间、结果、必要的关联标识和配额结果，用于审计与故障定位；不得记录密钥、完整签名材料、访问令牌或敏感请求体。
- **按应用配额**：配额以应用标识为独立维度配置、计数和限制，超限在适配边界拒绝并返回统一错误，不消耗业务资源；不得只设全局限流代替应用配额。

上述校验顺序必须保证任何鉴权、验签、时间窗或 nonce 校验失败的请求都不会产生业务副作用。

### 5. Webhook 签名、重试与幂等

Webhook 属于开放平台的推送适配能力，按至少一次投递语义设计，不以网络重试换取业务重复执行：

- **签名边界**：出站 Webhook 由 `channel` crate 按应用密钥生成 HMAC-SHA256 签名，并携带时间戳等防重放信息，由接收方验签；系统接收入站 Webhook 时，也必须在 `channel` crate 验签后才能转换成统一事件。业务层不处理原始签名，密钥管理与日志脱敏遵循开放平台要求。
- **重试边界**：超时、网络失败或约定的可重试响应由 `channel` crate 执行有上限、带退避的重试；达到终态后记录失败并提供可观测信息。重试沿用同一事件标识和业务载荷，可按签名要求更新时间戳，但不得创建新的业务事件。
- **幂等边界**：每次 Webhook 事件具有稳定唯一的事件标识，供接收方去重；发送方重试不得改变该标识。系统作为接收方时，业务消费端按该标识幂等，重复事件返回已处理结果而不重复入账、发货或发送领域副作用。
- **职责分界**：适配层负责 HTTP 收发、签名或验签、响应判定与重试；业务层负责统一事件内容、业务处理和幂等记录。适配层不能因收到重复事件而自行推断业务已成功，业务层也不能直接实现渠道 Webhook 客户端。

具体重试间隔、次数和存储方案在 P14 实现契约中确定，本 ADR 不虚构相关能力已经落地。

### 6. 版本、契约与破坏性变更

新增可选字段等向后兼容变更可在现有版本中演进；删除字段、重命名字段或改变既有语义属于破坏性变更，必须使用新版本路径（如 `/api/v2`），不得在原路径静默切换行为。

任何破坏性变更必须在发布前完成以下事项：

1. 生成并评审 `openapi.json` 的 OpenAPI diff，明确变更项、影响调用方和迁移方式，不得以人工说明替代契约差异评审。
2. 从新契约重新生成受影响的前端及渠道 SDK，并同步更新调用方；不得手写重复契约掩盖漂移。
3. 新旧版本同时提供至少 **30 天兼容期**，需要双写的场景在兼容期内保持双写和一致性行为，并提供旧版本迁移说明。

30 天是最短兼容窗口而非自动删除期限；只有在窗口届满且迁移条件满足后，才能另行评审旧版本下线。兼容期内回滚新版本时，旧版本及其契约必须仍可服务。

## 后果

### 正面影响

- 业务用例只维护一套流程和统一错误语义，新增渠道主要增加适配器及契约测试，不再复制业务分支。
- 登录、支付、分享、推送、扫码和归因的职责可独立审查，第三方 SDK 与协议变化被限制在 `channel` crate。
- OAuth2、HMAC-SHA256、时间窗、nonce、日志和应用配额形成明确的开放平台安全基线；Webhook 至少一次投递与业务幂等相配合，降低重复副作用风险。
- OpenAPI diff、SDK 重生成和至少 30 天兼容期使破坏性变更可发现、可迁移、可回退。

### 代价与风险

- 需要维护统一模型、适配契约、渠道能力矩阵和错误映射；简单渠道也必须经过适配层，短期实现成本高于直接分支。
- 统一上下文不能承载所有渠道细节，未来扩展字段必须保持向后兼容，且不得演变成包含渠道专有任意数据的旁路。
- nonce 去重、事件幂等、配额和 Webhook 重试需要可靠状态存储及清理策略；若事件标识不稳定或重试绕过幂等，仍可能产生重复副作用。
- 多渠道壳只能解决协议与能力差异，不能允许适配层吞并业务规则。代码评审和依赖边界检查必须持续禁止业务代码按渠道分叉。

## 回滚

本 ST 仅新增决策文档，没有渠道运行态、适配器或配置可供回滚。若该决策需要替换，应以新的 ADR 说明原因并 supersede 本文档，保留历史决策，不通过直接改写历史记录掩盖演进过程。

P14 实现后，如某一渠道适配出现阻断性故障，可在 `channel` crate 的接入边界停止该渠道的流量或新能力发布，保留统一业务接口和 `ChannelContext` 不变，并恢复上一兼容版本的适配实现；不得把临时 `if channel == ...` 分支加入业务层作为回滚手段。开放平台回滚期间继续执行验签、防重放、调用日志、配额与 Webhook 幂等，已接收事件不得因回滚重复产生业务副作用。破坏性 API 变更回滚时，旧版本在约定的至少 30 天兼容期内保持可用，SDK 与 OpenAPI 契约同步回退或重新生成，避免文档、客户端和服务端版本错位。
