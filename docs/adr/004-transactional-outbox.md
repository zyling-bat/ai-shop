# ADR-004 事务消息与 Transactional Outbox

- 状态：已接受（Accepted）
- 日期：2026-11-25
- 阶段：P0 / ST-0.5（业务实现归 P5）
- 关联约束：ST-0.5 R1、02 §2.14（幂等、事件、锁）、06 §6.3.5（outbox 写入）

## 背景

业务数据提交与事件投递若分别写入数据库和外部消息通道，任一步骤失败都会造成双写不一致：业务已提交但事件丢失，或事件已投递但业务未提交。需要在不引入分布式事务的前提下，保证业务事实与待投递事件同源、同生共死，并允许异步重试。

本 ADR 在 P0 / ST-0.5 仅固化 transactional outbox 的决策与实现边界，目标数据模型沿用 `outbox_event` 的 `event_id`、事件内容、`status`、`retry_count`、`next_retry_at`、`sent_at` 及 `(status, next_retry_at)` 索引约定。**本阶段不新增表或迁移，不实现 outbox worker、消息投递或消费者；业务实现统一归 P5，ADR 落盘不代表这些能力已经交付。**

## 决策

### 1. 采用 transactional outbox，业务与事件同事务

- 业务数据与对应的 `outbox_event` 必须在**同一个 PostgreSQL 事务**中写入；任一写入失败，整个事务回滚，不允许只保留其中一方。
- 事件先作为数据库中的待投递事实保存，再由后续 worker 在事务提交后异步读取并投递。数据库是事件待处理状态的权威来源，不以内存队列、Redis 或一次外部调用成功与否代替该事实。
- 选择 transactional outbox 是为了消除数据库与消息通道之间的双写原子性缺口，同时保留异步解耦和失败重试能力；不采用跨数据库与消息通道的分布式事务，也不采用“业务提交后直接发送并期待发送成功”的方案。

### 2. 写入幂等与外部副作用边界

- `event_id` 使用 UUID 并保持唯一，同一逻辑事件重试写入时沿用同一个 `event_id`。
- 事件写入遇到 `event_id` 冲突时使用 `ON CONFLICT (event_id) DO NOTHING`，不得因重复写入生成另一条事件。
- **数据库事务内禁止 HTTP、Redis 或模型调用。** 这些外部调用既不能参与数据库事务回滚，也会延长事务和连接占用时间；事件投递及其他外部副作用只能发生在事务提交之后。
- 该模式提供至少一次投递语义，不宣称端到端“恰好一次”。提交后若外部投递成功但状态回写失败，同一事件可能再次投递，必须由消费者幂等兜底。

### 3. 批量获取、状态机与重试

worker 按 `status = pending` 且 `next_retry_at <= now()` 获取到期事件，按 `created_at` 排序，每批最多 100 条；使用 `(status, next_retry_at)` 索引支撑获取。状态语义固定如下：

| 状态 | 语义与迁移 |
|---|---|
| `pending` | 待发送，或已到 `next_retry_at`、可再次被批量获取的重试事件。 |
| `sent` | 发送成功；记录 `sent_at`，不再进入常规重试。 |
| `failed` | 最近一次发送失败但仍可重试，**不是终态**；递增 `retry_count`，以指数退避计算下一次 `next_retry_at`。到期后在进入下一轮投递前恢复为 `pending`，仍由上述 `pending + next_retry_at` 条件统一获取，不得绕过退避立即重发。 |
| `dead` | 失败次数超过 8 次，即 `retry_count > 8` 时进入的终态；停止自动重试并触发告警，保留事件供排查与后续人工处置。 |

发送成功必须置为 `sent`；发送失败必须递增 `retry_count` 并执行指数退避。达到 `dead` 条件时不得继续按普通失败排程，告警至少应能关联到 `event_id`，避免静默丢失。

### 4. 消费者按 event_id 幂等

- 每个消费者必须以 `event_id` 作为幂等键识别重复事件；无论事件因重试、状态回写失败还是人工恢复而再次到达，都不得重复产生业务副作用。
- 消费者的去重记录与其业务写入应在同一数据库事务中提交，避免“业务已生效但去重记录丢失”或反向不一致。
- 生产端 `event_id` 冲突时 `DO NOTHING` 只解决事件记录重复写入，不能替代消费端幂等。

## 后果

- 正面：业务数据与待投递事件具有相同的数据库原子性边界；外部通道短时不可用不会迫使业务事实与事件状态分叉；异步批量投递、指数退避和 `dead` 告警提供了可恢复的失败路径。
- 负面：投递存在轮询延迟和数据库读取负载；至少一次投递会产生重复消息，消费者必须承担幂等成本；`dead` 事件需要告警响应和人工处置，不能仅依靠自动重试。
- 事务回滚边界：业务事务提交前发生失败，业务数据与事件一起回滚；事务提交后，数据库回滚不能再撤销已经发生的 HTTP、消息或其他外部副作用，后续只能依靠重试、消费者幂等或明确的补偿流程处理。
- 文档回滚边界：本 ST 只新增决策文档，没有对应表、迁移、worker、消费者或业务代码需要回滚。未来 P5 的实现及其 schema、部署和运行回滚必须在对应变更中单独设计与验证，不得以撤回本 ADR 代替运行时回滚。
