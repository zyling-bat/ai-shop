# ADR-006 前端形态与契约生成

- 状态：已接受（Accepted）
- 日期：2026-11-25
- 阶段：P0 / ST-0.5（前端业务实现归 P14）
- 关联约束：00 A4（技术栈锁定）、00 A5（workspace 与分层）、03 §3.5（版本与兼容）、ST-0.5 R3

## 背景

商城、后台、H5、小程序和移动 App 需要复用页面逻辑与设计系统，同时保留各渠道的原生能力。A4 已锁定 Leptos 0.7、Tauri 2 mobile 与 utoipa 契约链路；本 ADR 固化各端形态及兼容边界，避免后续按端另选框架或手写重复契约。

本 ADR 只交付决策，不代表前端功能已经实现。

## 决策

### 1. 阶段与交付边界

- 本 ST 仅确定技术形态、契约来源和变更规则；Web 商城、后台、H5、小程序、移动 App、共用设计系统、原生桥接及前端 SDK 的业务实现均归 P14。
- 本 ST 不新增前端工程、页面、组件、依赖、构建链路、原生壳、桥接代码、SDK 或 SDK 生成物，不声称 P14 功能已交付。
- 前端应用的工作区位置遵循 A5；渠道协议与能力差异只能落在 `channel` 层，不得把渠道判断扩散到业务层。

### 2. Web 商城与后台

- Web 商城与后台统一使用 **Leptos 0.7 SSR+CSR**：服务端渲染承担首屏输出，客户端水合后承担交互，不为商城和后台分别选择不同前端框架。
- 两端共用同一套设计系统，包括设计令牌、基础组件及交互规范；业务页面可以不同，不得 fork 出两套互不同步的基础组件体系。
- 两端均从同一份 `openapi.json` 生成 SDK 与契约类型，不各自维护请求响应模型。

### 3. H5 与小程序

- H5 与小程序统一复用 **Leptos CSR 产物及页面逻辑**；小程序使用**小程序原生壳**承载，壳层负责调用小程序原生能力。
- H5 与小程序共用业务页面逻辑，登录、支付、分享、订阅消息、扫码等能力差异由壳层和 `channel` 适配，不在业务页面中散落渠道分支。
- **明确不使用 Taro**，也不得以 Taro 兼容层、运行时或 DSL 替代上述 Leptos CSR + 原生壳方案。

### 4. 移动 App

- 移动 App 使用 **Tauri 2 mobile**，复用 Leptos 的页面与应用逻辑，不另建一套独立前端技术栈。
- 支付、推送和扫码通过 Tauri 2 mobile 的原生桥接调用平台能力；桥接只负责协议与能力适配，业务规则仍由既有应用层和 `channel` 边界约束。
- iOS/Android 的原生差异封装在桥接与渠道适配内，不在共享 Leptos 业务逻辑中按平台复制业务流程。

### 5. OpenAPI 唯一契约事实源

- 由 **utoipa 生成的 `openapi.json`** 是前后端 API 契约的唯一事实源。
- 所有前端 SDK、请求/响应类型和客户端接口必须由该 `openapi.json` 生成；生成物不得手工修改后充当另一份契约。
- 禁止在前端手写并长期维护第二套 DTO、接口类型、API client 或 OpenAPI 描述，也禁止在生成物之外保留与之平行的“临时类型”。契约变化必须先体现在 utoipa 生成链路，再重新生成前端产物。

### 6. 版本与破坏变更

- 新增可选字段等向后兼容变更可在现有版本内演进；删除字段、修改字段语义或其他破坏性变更必须采用新版本路径（如 `/api/v2`），遵循 03 §3.5。
- 破坏性变更合入前必须完成并评审 **`openapi.json` diff**，识别受影响调用方，并从更新后的契约**重新生成全部受影响的前端 SDK 与类型**；不得以手改生成物代替重生成。
- 新旧版本必须并行提供**至少 30 天兼容期**，并按 03 §3.5 执行兼容期双写。兼容期内继续提供旧版契约及对应客户端可用性，不得在新版发布时立即删除旧版。
- 兼容期届满后，只有确认受影响前端已切换到重新生成的 SDK，才可移除旧版本；30 天是最低期限，不缩短为构建或发布间隔。

## 备选方案

| 备选方案 | 为何不选 |
|---|---|
| Web 商城与后台分别采用 React、Vue 或其他框架 | 违反 A4 的 Leptos 0.7 锁定，分裂组件、状态管理与构建体系，也难以维持同一设计系统；更换须另行书面批准 |
| Web 仅 CSR 或仅 SSR | 仅 CSR 不利于商城首屏与搜索可见性；仅 SSR 不足以统一承载客户端交互。SSR+CSR 在统一 Leptos 组件体系下兼顾两者 |
| H5/小程序使用 Taro 或 uni-app | 会引入另一套 DSL、运行时和组件生态，破坏 Leptos 页面逻辑复用；A4 明确不使用 Taro，原生壳也更直接地隔离渠道能力 |
| 移动 App 使用 Flutter、React Native 或分别开发原生界面 | 需要维护额外的 UI 与技术栈，无法充分复用 Leptos；Tauri 2 mobile 同时保留复用路径和支付、推送、扫码的原生桥接能力 |
| 前端手写 TypeScript/Rust 类型与 API client，或单独维护一份 OpenAPI 文件 | 会形成第二套契约事实源，与服务端注解和实际接口漂移；生成链路使契约变更可 diff、可重建、可评审 |
| 破坏性变更直接替换旧接口，发布后再修前端 | 会使已发布客户端立即失效，绕开兼容期与双写要求；破坏变更必须先 diff、重生成 SDK 并并行兼容至少 30 天 |

## 后果

- 正面：商城与后台共享 Leptos 和设计系统，H5/小程序复用 CSR 页面逻辑，App 复用 Leptos 并保留原生能力；各端从同一契约生成 SDK，降低接口漂移与重复维护。
- 代价：需要维护 SSR+CSR、CSR 原生壳和 Tauri mobile 多目标构建与测试；设计系统和共享逻辑必须控制渠道分支，原生桥接仍需承担平台适配与发布成本。
- 约束：契约、SDK 与前端发布必须协同评审。破坏变更增加 OpenAPI diff、SDK 重生成和至少 30 天双版本维护成本，但这是强制兼容门槛，不得以交付进度为由省略。
- 当前状态：上述工程与运行能力均未由本 ADR 实现，P14 仍需按本决策实施并提供对应验证证据。

## 回滚

- 本 ST 只有决策文档，没有前端运行态、数据或生成物需要回滚；撤回本决策不等于已经交付或删除任何前端功能。
- P14 实施若需回退，应按已发布版本回退 Web、H5/小程序壳、移动 App 及原生桥接，并恢复上一版 `openapi.json` 后重新生成 SDK，禁止用手写类型修补回滚版本。
- 已发布的破坏性 API 即使发生前端回滚，也必须履行剩余兼容承诺，旧版本并行时间不得少于 30 天；不得因回滚提前撤下仍被客户端使用的旧接口。
- Leptos、原生壳、Tauri 2 mobile 或 utoipa 契约链路的替换不属于普通版本回滚，必须另立 ADR 评审，并按 A4 取得书面同意。
