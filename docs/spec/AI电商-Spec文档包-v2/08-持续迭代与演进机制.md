# 08 · 持续迭代与演进机制

> 这份文档回答一个问题：**这套系统交付之后，能不能在不改代码、不发版、不重建库的前提下持续加东西？**
> 判断标准只有四条可验证的：能不能只改配置上新功能？能不能灰度并秒级回滚？能不能只加一个适配器就换供应商？能不能只加一个消费者就接新下游？四条都"能"，才叫可迭代。

---

## 8.1 六个扩展点（系统的"插座"）

每个扩展点的共同约定：**编译期注册 + 配置选择 + 启动校验 + 运行期可切换**。不做动态热加载（Rust 下用 WASM 只在 M2 评估），避免为"可扩展"付出过度设计的代价。

| # | 扩展点 | 抽象方式 | 加东西的成本 | 兼容规则 |
|---|---|---|---|---|
| 1 | 业务规则（优惠/运费/佣金/税率/限购） | 数据驱动：`promotion_rule`、`freight_template_rule`、`commission_rule`、`tax_rate_config` | 后台配一条记录，0 行代码 | 规则 schema 版本化；旧规则字段只加不改 |
| 2 | 状态机迁移 | 集中迁移表 + 扩展动作枚举 | 加一个 `(from, action) → to` 映射 + 单测 | 已有迁移不得改语义；新增状态必须默认可达终态 |
| 3 | 外部供应商（支付/短信/推送/存储/搜索/运力） | 端口 trait + adapter | 加一个 `impl`，配置里指定 id | trait 方法只加默认实现；adapter 必须通过同一套契约测试 |
| 4 | 事件下游 | outbox + `consumer` 注册表 | 加一个消费者，声明 `event_type` 与幂等键 | 事件 payload 只加字段；消费者按 `event_type + version` 订阅 |
| 5 | 渠道 | `channel` adapter（Web/H5/小程序/App/开放平台） | 加一个 adapter + 能力矩阵声明 | 业务层只见 `ChannelContext`；禁止业务分支渠道 |
| 6 | AI 能力 | `ai-gateway` provider + `ai-agent` 工具注册 + prompt 版本 | 加 prompt 版本或加一个工具，业务层不改 | prompt 必带评测基线；工具必须声明读/写与权限 |
| 7 | 前端楼层/组件 | 组件注册表（`component_type` → 渲染器 + 配置表单） | 加一个组件 = 加渲染器 + 表单 schema | 配置 schema 版本化，旧装修数据必须仍可渲染 |
| 8 | 开放平台 | OpenAPI + Webhook | 加一个接口或事件订阅 | 版本化路径 + 签名 + 配额 |

**注册表机制（统一实现）**

```rust
pub trait Extension: Send + Sync {
    fn id(&self) -> &'static str;          // 如 "sms.aliyun"
    fn kind(&self) -> ExtensionKind;       // Payment / Sms / Search / Model / Channel ...
    fn capabilities(&self) -> Capabilities;
}

pub struct Registry { /* 启动期注册，运行期只读 + 可原子替换默认项 */ }
impl Registry {
    pub fn register(&self, ext: Arc<dyn Extension>) -> Result<(), RegistryError>;
    pub fn resolve(&self, kind: ExtensionKind, id: &str) -> Result<Arc<dyn Extension>, RegistryError>;
    pub fn set_default(&self, kind: ExtensionKind, id: &str) -> Result<(), RegistryError>; // 热切换
}
```

启动校验：配置里引用的 `id` 必须已注册，否则拒绝启动并打印可用清单（避免"配置写错、静默降级"）。

## 8.2 演进兼容矩阵（什么能改、什么不能改）

**数据库**

| 变更 | 安全性 | 做法 |
|---|---|---|
| 加表 | 安全 | 新迁移文件，独立主题 |
| 加列（可空或带默认） | 安全 | 先加列 → 双写 → 回填 → 再加非空约束 |
| 加索引 | 安全（注意锁） | `CREATE INDEX CONCURRENTLY` |
| 加枚举值 | 安全 | 状态列 CHECK 约束同步扩展；**所有读方必须容忍未知值** |
| 改列类型/改名 | 破坏性 | 加新列双写回填，旧列保留 ≥1 个发布周期再删 |
| 改语义（同名列不同含义） | 禁止 | 一律新建列，不允许复用 |

**API**

- 加字段、加可选参数、加新端点：安全。
- 删字段、改类型、改语义、改错误码含义：必须 `/api/v2` + 双跑 ≥30 天 + 客户端迁移清单。
- 错误码只增不改；废弃错误码保留并标记 `deprecated`，前端遇到未知错误码统一走兜底文案。
- **前端必须容忍未知枚举值**（`match` 必须有 `_ => 降级展示`），否则后端加一个状态就白屏——这是最常见的迭代事故。

**事件**

- `payload` 只加不改；消费者按 `(event_type, version)` 订阅，未知版本进死信并告警。
- 事件名不复用；下线事件先停发 1 个周期再删订阅。

**Prompt 与模型**

- prompt 版本化，升版本必须附评测结果且不下降；回滚 = 改版本号。
- 换模型只改 `sys_config` 映射；新模型必须先在 `evals` 上跑通同分基线。

## 8.3 功能生命周期（防止开关僵尸）

```
提案 → flag 创建(默认 false) → 内部灰度 → 1% → 10% → 50% → 100%
     → 稳定 2 个周期 → 移除 flag 与旧分支代码
```

纪律三条：

1. 每个 flag 必须有 `owner`、`created_at`、`expire_at`、`cleanup_ticket`。
2. flag 数量上限（建议 50），超限必须清一批才能加新的。
3. 全量 2 个周期后必须清理旧代码分支——**flag 不是永久架构，是临时开关**。

`feature_flag` 表在 02 已有，这里补生命周期字段：`state(created/ramping/full/stable/removed)`、`owner`、`expire_at`、`cleanup_ticket`。

## 8.4 迭代节奏（发布列车的建议）

| 类型 | 频率 | 内容 | 冻结窗口 |
|---|---|---|---|
| 常规发版 | 每 1–2 周 | 功能 + 修复，走 flag 灰度 | 大促前 7 天冻结 |
| 配置变更 | 随时 | 活动、券、运费、佣金、楼层 | 无需发版，需审批与回滚预案 |
| Prompt/模型变更 | 每周 | 走评测 + 灰度比例 | 大促前冻结 |
| 数据库迁移 | 随发版 | 只追加，迁移与代码同批上线 | 大促前冻结 |
| 紧急修复 | 随时 | 走 hotfix 分支 + 回滚预案 | 无 |

**回滚优先级**：先关 flag（秒级）→ 再回滚配置 → 再回滚镜像（分钟级）→ 最后才回滚数据库（尽量避免，靠"只追加"避免需要）。

## 8.5 可迭代性的验收演练（Gate 之外的"能力证明"）

这四个演练是**证明系统真的能持续迭代**的唯一方式，建议在 P16 阶段各做一次并留档：

**演练 A｜只改配置上新活动**
不写一行代码，在后台配一个"满 300 减 50、限品类、限量 1000 份"的活动并上线；验证券可领、可核销、预算耗尽熔断；再一键下线，验证已领券按规则失效。**通过标准：全程 0 行代码、可回滚、有审计。**

**演练 B｜只加适配器换供应商**
新增一个短信 adapter（如从 A 厂商换到 B 厂商），只加 `impl` + 配置切换 + 契约测试，业务代码 diff 为 0。**通过标准：切换后验证码送达率正常，回切 1 分钟内完成。**

**演练 C｜只加消费者接新下游**
新增一个消费者，把 `order.paid` 事件同步到一个新的数据仓库/外部系统，不改主链路。**通过标准：事件不丢、不重、可按 `event_id` 重放补齐。**

**演练 D｜只改 Prompt 版本切换风格**
把客服回答风格从"简洁"切到"详细"，走评测 → 灰度 10% → 50% → 100% → 回滚。**通过标准：评测分数不降、可秒级回滚、日志可按版本归因。**

这四条全过，才敢说这套系统"能持续迭代"。任何一条做不到，说明对应的扩展点只是文档上的，实际没落地。

## 8.6 明确不做的"可扩展"（避免过度设计）

- **动态插件热加载**：Rust 生态下收益小于成本，M2 再评估 WASM 沙箱。
- **可视化建模 DSL / 低代码表单引擎**：会把简单问题复杂化，规则表 + 楼层组件已经够用。
- **微服务拆分**：单库单体的模块化边界（crate + 端口 trait）已足够支撑到日 20 万单，拆分按实际瓶颈做，不按"将来可能要"做。
- **多租户物理隔离**：先做逻辑多租户（`tenant_id` + 数据权限），真有合规要求再上独立库。
- **全量事件溯源**：只在订单/支付/结算做状态日志，不做全域 event sourcing。
