# 07 · 排期与资源估算

> 估算口径：**以一个有 Rust 经验、不熟悉本业务的开发者**为基准（1 人日 = 6 小时有效编码）。Trae 能显著提升编码速度，但**不能压缩**需求确认、联调、压测、合规、审核的时间，这些仍按人日计。

## 7.3 关键路径与并行建议

```
P0 → P1 → P3 → P4 → P5 → P6 → P9 → P16 → P17
                ↘ P7 ↗        ↗
P0 → P11 → P12 → P13（可与 P4–P8 并行，只要接口未冻结前先定 trait）
P10（内容/客服）依赖 P2，可与 P5 并行
P14 前端依赖各域接口，建议 P3 完成后即启动商城骨架，边做边接
```

并行原则：**后端交易链路是串行关键路径，AI 与前端是可以并行的两条副线**。三个人的最优分工是：一人交易+结算，一人 AI+渠道，一人前端+后台。

## 7.5 容易被低估的五件事（排期时必须加缓冲）

1. **前端**：六端（Web/H5/小程序/App/后台/商家后台）占了总工作量 1/3，最容易按"页面数×0.5 天"低估。
2. **支付联调**：商户号申请、证书、回调白名单、沙箱与生产差异，通常要 1–2 周等待，不是编码时间。
3. **结算分账**：分账机构接入有审核周期；对账差异处理是长期运营成本，不是一次性功能。
4. **合规与审核**：小程序类目资质、App 上架、AIGC 标识、隐私政策，每项都可能卡 1–3 周。
5. **数据与埋点**：口径不统一会导致后面所有看板返工，必须在 P15 之前把指标字典定死。

## 7.6 风险与决策点

| 风险 | 触发信号 | 处理 |
|---|---|---|
| 范围失控 | 每个阶段都"顺手加个功能" | 只按 `01` 的 M0 清单做，新需求进 backlog 并标级别 |
| AI 效果不达标 | 评测分数低于门槛 | 降级为规则方案先上线，AI 转 M1 |
| 结算合规卡住 | 分账机构接入受阻 | 先做"平台代收 + 人工结算"临时方案（需明确合规口径）并限制规模 |
| 前端拖期 | 接口频繁变更 | 冻结 `openapi.json`，变更走版本；先做骨架再接数据 |
| 单人开发倦怠/中断 | 进度停滞 | 按里程碑交付可运行片段，不做"半年后一次上线" |

---

## 7.7 建议的开工顺序（如果只做一件事）

先做 **P0 + P1 + P5（价格引擎 + 下单 + 库存预占）**。理由：这三段决定系统能不能成立，其余模块都是围绕它们生长。价格引擎和库存一旦返工，后面所有域都要跟着改。
